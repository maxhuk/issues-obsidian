# Issues in Obsidian

Issues are Markdown notes inside project folders of an Obsidian vault. Each project folder holds a project note, an `AGENTS.md` written by the Issues plugin, an `Issues/` folder with one note per issue, and, when the project tracks releases, a `Releases/` folder. Everything is done by reading and writing those files; Obsidian picks up changes on its own.

## Configuration

Edit this block once per machine. Everything else is discovered.

```yaml
roots:
  - /path/to/vault/Projects
```

`roots` lists the folders that contain project folders. Add a line for every vault or area that holds projects.

## Discover the projects

Do this at the start of any issue-related request; never rely on a remembered list.

```bash
for root in /path/to/vault/Projects; do
  grep -l -E '^type: project$' "$root"/*/*.md 2>/dev/null
done
```

Each hit is a project note. Its folder is the project folder; the `project:` line in its frontmatter is the key, for example `BRE`. Resolve what the user names by key (`BRE`), by folder name (`Breathe`), or by a close match of either, case-insensitively. When two projects could match, ask.

## Before any write, read the project's AGENTS.md

`<project folder>/AGENTS.md` is generated by the plugin from that project's configuration and is the authoritative contract: the exact frontmatter to write, the status vocabulary and its order, which statuses are closed, folder paths, the release procedure, and the mistakes to avoid. Follow it to the letter; it overrides anything below.

If the file is missing, the project has never been opened in Obsidian with the plugin enabled. Ask the user to open the project note once, which writes the file, rather than guessing the rules.

## Requests and what they mean

**"Add X as a bug in BRE"** (also task, issue, ticket)
1. Discover projects, pick `BRE`, read its `AGENTS.md`.
2. Next number: highest `BRE-n` in the issues folder plus one.
3. Create `Issues/BRE-<n>.md` with the frontmatter the guide prescribes: `type: bug` or `task`, `status` as the guide's first open status unless the user named one, `created` today, no `order`.
4. Body: one or two short paragraphs from what the user said. Do not pad.
5. Reply with the key and the path.

**"Move BRE-12 to doing" / "mark BRE-12 done" / "cancel BRE-12"**
Change `status` and apply the guide's status rules: remove `order`, set or clear `closed`, set or clear `release`. Leave everything else untouched.

**"What's open in BRE?" / "what am I doing on Breathe?"**
Read the frontmatter of every note in the issues folder, drop closed statuses unless asked, group by status in the guide's order, and list key, title and labels. Keep it to a glance.

**"Add a note to BRE-12" / "log progress"**
Append to the body under a dated heading (`## YYYY-MM-DD`). Never rewrite existing body text.

**"Plan 1.5.0 for BRE" / "ship 1.5.0"**
Follow the Releases section of the guide exactly: a planned release note, then the ship procedure that moves every merged issue into it. Projects with releases off have no such section; say so.

**Issue keys in conversation** (`BRE-12`)
Open the note and use its title and status as context before answering.

## Rules

- Never write `order`, never rename an issue file, never change `project`.
- Dates are `YYYY-MM-DD`. Wikilinks are quoted: `parent: "[[BRE-100]]"`.
- Use the issue key in commit messages and branch names when working in a code repository for that project.
- Do not open or drive Obsidian; file edits are enough and sync to other devices through the vault.
- When unsure which project, status or type the user means, ask with the options you discovered rather than guessing.
