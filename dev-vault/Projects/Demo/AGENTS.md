# Working with Demo issues

Generated by the Issues plugin 0.1.0 from the project note. The plugin rewrites this file whenever the project's configuration or the plugin changes, so edits here are lost; project-specific guidance belongs in the project note's body.

Issues are plain Markdown notes with YAML frontmatter. The Issues plugin renders them as a list and writes the same frontmatter you write by hand. Reordering rows is the one thing that has no file-level form: it is done in the plugin, by drag or the row menu.

## Where things are

- Project note: `Projects/Demo/Demo.md` (key `DEMO`). Its frontmatter is the configuration this file was rendered from.
- Issues: `Projects/Demo/Issues/`, one note per issue, file name `DEMO-<number>.md`.
- Releases: `Projects/Demo/Releases/`, one note per version, file name `DEMO-<version>.md`.
- Attachments: `Projects/Demo/Issues/Attachments/`, embedded from issue bodies with `![[file]]`.

## Statuses, in order

| Status | Kind | Meaning |
|---|---|---|
| `inbox` | open | Captured, not yet looked at. |
| `backlog` | open | Understood, not chosen. |
| `next` | open | Chosen to be done soon. The pull list. |
| `doing` | open | In progress. |
| `pr` | open | A pull request is open. |
| `merged` | open | Landed on the main branch, not yet in a release. |
| `released` | closed | Shipped in a release. |
| `canceled` | closed | Will not be done. |

Releases are on. `released` ties an issue to a release note; shipping a release sweeps every issue in `merged` into it. Issues in a closed status other than `released` disappear from the list 14 days after closing (they are not deleted).

## Create an issue

1. List the files in `Projects/Demo/Issues/`, take the highest `DEMO-n` number and add one. Create the folder if it does not exist.
2. Create `Projects/Demo/Issues/DEMO-<n>.md`. If the path already exists, you raced another writer: recompute and retry.

```markdown
---
title: Fix timer drift on iOS
project: DEMO
type: task
status: inbox
priority: medium
labels: []
created: YYYY-MM-DD
---
What is wrong or wanted, how to reproduce for a bug, and what done looks like.
```

Rules for the frontmatter:

- Write `title`, `project`, `type`, `status`, `priority`, `labels`, `created`. This is what the plugin itself writes, minus `order`.
- `project` is `DEMO`, verbatim.
- `type` is `task` or `bug`.
- `status` is one of the statuses above. Use `inbox` for something captured but not understood, `backlog` for understood work, or go straight to `doing` when starting on it.
- `priority` is `high`, `medium` or `low`.
- `created` is today as `YYYY-MM-DD`.
- `parent`, when used, is a quoted wikilink to another issue in this project: `parent: "[[DEMO-100]]"`.
- **Do not write `order`.** The plugin owns it. An issue without `order` sorts after every ordered row in its section, which is where fresh work belongs.
- Do not write `closed` or `release` on creation unless the status requires them (see the status rules).

The body is Markdown. Keep it short; the title carries the row. Attach files by pasting them into the note in Obsidian, or by placing them in `Projects/Demo/Issues/Attachments/` and embedding them with `![[file]]`.

## Change status

Set `status` to another value from the table, **remove `order`** so the issue lands at the bottom of its target section, and apply these rules. "Closed" means `released`, `canceled`.

| Transition | Also do |
|---|---|
| Open → closed | Set `closed` to today (`YYYY-MM-DD`). |
| Closed → closed | Keep `closed`. |
| Closed → open | Remove `closed`. |
| Into `released` | Also set `release` to a quoted wikilink to the release note, `release: "[[DEMO-1.5.0]]"`. Use this for a single issue that went out on its own, for instance in a hotfix. When a whole version went out, ship the release (below) so the release note and all `merged` issues change together. |
| Out of `released` | Also remove `release`. |

An agent may drive an issue through the whole cycle, forwards and backwards. Moving an issue to `canceled` with `closed` set is how an invalid issue is retired; nothing is deleted.

## Edit an issue

- Change `title`, `type`, `priority`, `labels`, `parent` and the body freely.
- Never rename the file, change `project`, or write `order`.
- Append to the body rather than rewriting it when adding progress notes. A dated heading (`## YYYY-MM-DD`) is enough.
- Use the issue key (`DEMO-123`) in commit messages and branch names; that is the only cross-reference that exists.

## Releases

Release notes live in `Projects/Demo/Releases/`, one per version, named `DEMO-<version>.md`. The key prefix keeps wikilinks unique across projects.

### Plan a release

Create `Projects/Demo/Releases/DEMO-1.5.0.md` (creating the folder if needed):

```markdown
---
type: release
project: DEMO
version: 1.5.0
status: planned
---
```

The body is free Markdown for release notes and may stay empty.

### Ship a release

This is what the plugin's Ship button does. Do it after the build is live, in this order:

1. On the release note: set `status: released` and `released` to today. Create the note in that state if no planned note exists.
2. For every issue of this project whose `status` is `merged`: set `status` to `released`, `release` to `"[[DEMO-<version>]]"`, `closed` to today, and remove `order`.

If some `merged` issues must stay out of the release, move them to another status first. If step 2 is interrupted, run it again: the issues still in `merged` are exactly the unshipped ones.

### Changelog text

```
- <title of task 1>
- <title of task 2>
Fixes
- <title of bug 1>
```

Tasks first, then bugs under a `Fixes` line that is omitted when there are no bugs; within each group, issues with `order` ascending, then those without by `created` ascending. The plugin's "Copy changelog" produces exactly this.

### Undo a release

Set the release note back to `status: planned` and remove `released`; on each issue whose `release` names that note, set `status` to `merged` and remove `release`, `closed` and `order`.

## What breaks the list

- A duplicate key, from not recomputing the number after a collision.
- A `status` value that is not in the table. The issue lands in an extra section headed by that value until fixed.
- A hand-written `order`. The row lands at an arbitrary position in its section.
- `closed` present on an open issue, or missing on a closed one.
- A released issue without `release`, or a release note marked `released` while its issues still sit in `merged`. Ship both sides together.
- Unquoted wikilinks in `parent` or `release`. YAML needs `"[[DEMO-100]]"`.
- Dates in any format other than `YYYY-MM-DD`.
- A release note named without the key prefix. `[[1.5.0]]` is ambiguous across projects.

Direct file edits are picked up by Obsidian within a second, including through Obsidian Sync from another device. When Obsidian is running on this machine, its command-line interface can create files and set properties through the app instead; the rules above are the same either way.
